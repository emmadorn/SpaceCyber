cFS: Exploiting the Command Ingest Module
1. What is the Command Ingest Module and how does it work?
  1. “ci_lab” (Command Ingest Lab) is responsible for receiving and processing the ground commands that are typically sent during mission operations. These commands may be sent to control various subsystems of the spacecraft (e.g., thermal, power, or communication)
  2. The Command Ingestor in cFS is responsible for receiving, interpreting, and validating commands.
2. What is the basic flow of how command get where they need to be?
  1. Ground sends the command
  2. Command Ingest Module processes the command
  3. Message is placed on the software bus
    1. The Software Bus is implemented as a message queue, and when a command is placed onto the bus, it is placed into the queue as a message.
    2. The message is then made available for subscribed apps or components to read and process.
    3. Message Routing: The SB service routes the message to the appropriate pipe based on the message ID. Each application subscribes to specific message IDs, so the SB service knows which pipe to send the message to
    4. The SB service maintains a subscription table that maps message IDs to the pipes of subscribing applications. This table is updated whenever an application subscribes to or unsubscribes from a message ID
  4. Application(s) meant to act on the command retrieve it from the bus
    1. Pipe Creation: Each application that needs to receive commands creates a pipe using the SB service. A pipe is essentially a queue that holds messages until the application processes them.
  5. Command Handler within the app process the command and tasks the action to be executes
    1. After executing the command, the application may generate a status message or telemetry data to indicate whether the command was successfully executed or whether an error occurred.
Example:
  1. Ground sends command: “Increase internal temperature 5 degrees”
  2. Command Ingest Module takes in the command and places it on software bus
  3. Thermal Application retrieves the command
  4. Thermal Application increases the internal temperature 5 degrees

  2. Modifying Message Content
    1. How can we modify messages being sent from the Command Ingest Module?
      1. 3 key components of messages to consider attacking:
        1. Message reception: command messages received on SB
        2. b. Message validation: validation of formatting, integrity and authorization
        3. c. Message routing: messages routed to appropriate app based on MID (message ID)
      2. Gaining access/control to a more trusted app that has access to higher level privileges might bypass certain safeguards
      3. Exploiting potential vulnerabilities in command packet validation
      4. May not be feasible to attack message routing directly due to high privilege level of the SB
    2. What does modifying messages do for the attacker?
      1. Privilege escalation: message fields related to level of access could be tampered with to make the system believe a low-privilege message has high-privilege access if measures aren’t taken in the validation of messages
      2. Data corruption: messages could have the potential of carrying malicious data that alter things such as telemetry, sensor, or mission data, leading to system processing incorrect values and result in corrupted logs, incorrect operational decisions, or the loss of mission data
      3. Create backdoors: messages could contain hidden functionality that would allow a backdoor to be created, potentially reconfiguring subsystems to accept malicious commands
